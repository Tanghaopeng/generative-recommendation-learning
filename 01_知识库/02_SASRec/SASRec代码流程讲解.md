# SASRec 代码流程讲解

这份说明对应实际下载的 `pmixer/SASRec.pytorch`，commit：
`b253407b3c5d6ec3201a39767a572f44fd5ef6d0`。
它是第三方 PyTorch 复现，作者原始 TensorFlow 实现在 作者原仓库（见文末链接）。
讲解依据本地源码；这里只做数据与代码核验，没有完整训练结果。

## 1. “SASRec 基线”究竟是什么

基线是后续生成式方法需要比较的普通推荐方法。SASRec 本身是一个可训练的推荐模型，
接收用户按时间排序的物品 ID，用自注意力学习历史中的依赖，再给候选物品打分。
这个版本从随机初始化学习物品向量与模型参数，不需要下载 7B 大模型，也没有预训练权重可直接推荐 Office Products。

例如，用户先后交互 `[笔记本, 中性笔, 文件夹]`，模型学习：
“在这段历史之后，下一件物品是什么？”
不同用户有不同历史，因此得到不同推荐；本版本模型的 `user_ids` 参数并未参与计算，
个性化主要由历史序列体现，并没有独立用户 embedding。

## 2. 三个主要文件

| 文件 | 主要职责 | 建议阅读顺序 |
|---|---|---|
| `baselines/sasrec/utils.py` | 读取数据、划分、样本生成、评估 | 先看 `data_partition`，再看 `sample_function` |
| `baselines/sasrec/model.py` | 物品/位置向量、自注意力、训练打分、推理打分 | `SASRec` → `log2feats` → `forward` → `predict` |
| `baselines/sasrec/main.py` | 参数、训练循环、损失、优化器、评估和保存 | 在了解前两个文件后看 |

本地行号：`utils.py:96` 数据划分、`:33` 样本生成、`:69` 多进程采样器、`:129` 测试评估、`:178` 验证评估。
`model.py:25` 模型类、`:65` 序列编码、`:97` 训练打分、`:111` 推理打分。
`main.py:93` 损失、`:119` 定期评估、`:129` 保存模型条件。

## 3. 原始 Amazon 数据如何进入它

评论文件一行一条 JSON。起步只取 `reviewerID`、`asin`、`unixReviewTime`、`overall`。
评论记录作为交互代理，并不是平台实际点击日志，也不是准确的购买时间。

本项目脚本 `scripts/prepare_office.py` 完成：

1. 读取全部 800,357 条官方 5-core 评论，读取到 gzip 末尾，检查压缩文件完整性。
2. 同一用户—物品保留最早记录，消除重复交互。
3. 重新迭代删除交互不足 5 次的用户与物品。
4. 将用户与物品映射为从 1 开始的连续数字 ID。
5. 每用户按时间排序，输出规范化交互、用户序列、共同划分和 SASRec 两列输入。

清洗后得到 86,713 个用户、25,898 个物品、677,247 条交互。
同时间戳用原文件行号打破平局，这是稳定的技术规则，不意味着知道同一天的真实先后。
所有评分都保留为隐式交互；如果改成只保留高评分，就必须重新过滤并另建实验版本。

SASRec 的输入是 `data/office2018.txt`，每行形如：

```text
1 120
1 95
1 603
2 18
```

这些数字仅是示意。第一列是用户 ID，第二列是物品 ID。
loader 不读取时间戳，也不会替你排序；它按文件出现顺序追加物品。因此上游输入之前必须完成时间排序。

## 4. 按用户分训练、验证与测试

`utils.py` 的 `data_partition()` 将长度至少 4 的序列划分为：

```text
完整历史：A B C D E F G
训练序列：A B C D E
验证目标：F
测试目标：G
```

本项目每用户至少有 5 个不同物品，都会得到训练、验证和测试目标。
验证输入是训练历史；测试输入是训练历史再加验证物品 F。
测试时看到 F，是因为预测 G 的时刻 F 已经发生；训练权重时不使用 F/G 作为监督目标。

共同划分保存在 `sequences.jsonl`。我们用原仓库实际的 `data_partition()` 逻辑核验两边完全相同，
未来 TIGER 直接用这份共同划分，避免两个模型处理出不同任务。

该协议是用户内时间划分，物品目录与 5-core 过滤来自整份离线数据，
不应宣称它完全模拟真实时间上线。严格时间实验以后单独增加。

## 5. 训练样本：历史右移一位

`sample_function()` 每次取一个用户的训练序列，构造 `seq`、`pos`、`neg`。
如果训练序列是 `A B C D E`，且 `maxlen=6`，则逻辑为：

```text
seq：0 0 A B C D
pos：0 0 B C D E
neg：0 0 X Y Z W
```

0 是左侧补齐用的 padding。
每个非零位置都学习“已看到当前物品及其更早历史后，下一物品是什么”。
例如 C 所在位置对应的正例是 D，该位置不能看到序列中的 D。

负例从物品目录随机抽取，排除该用户训练历史中的物品。未交互不等于用户真的不喜欢，
这是隐式推荐的采样假设；训练 sampler 不知道验证/测试目标，因此它们可能被抽为负例。

此实现每次使用训练序列尾部最多 `maxlen` 个预测位置，
不是显式遍历长序列里所有可能的滑动窗口。
`WarpSampler` 默认开 3 个进程，提前构造 batch，训练循环从队列取数据。

## 6. 模型怎样编码历史

`model.py` 中主要有两张向量表：

- 物品 embedding：数字物品 ID → 可学习的向量。
- 位置 embedding：历史序列位置 → 可学习的向量。

两者相加，经 dropout 后输入 Transformer 自注意力块。
用起步配置 `batch_size=32, maxlen=50, hidden_units=64` 举例：

```text
物品 ID：          [32, 50]
物品和位置向量：   [32, 50, 64]
自注意力编码结果： [32, 50, 64]
```

因果 mask 禁止当前位置关注未来位置；否则在预测 D 时直接看到 D，任务就发生泄漏。
模型还有前馈层、残差连接和 LayerNorm。本仓库有 `norm_first` 开关，
会影响归一化位置，实验报告应该记录是否开启，不能和不同版本结果不加区分地比较。

## 7. 如何训练：正例分数高、负例分数低

`forward()` 计算每个位置的历史表示与正例/负例物品向量的点积：

```text
正例分数 = 历史表示 · 正例物品向量
负例分数 = 历史表示 · 负例物品向量
```

`main.py` 使用 `BCEWithLogitsLoss`：正例标签为 1，负例标签为 0；仅 `pos != 0` 的位置参与损失。
目标可写成 `-log(sigmoid(s_pos)) - log(1-sigmoid(s_neg))`。
优化器是 Adam，默认学习率 0.001，betas 为 `(0.9, 0.98)`。

反向传播会更新物品 embedding、位置 embedding、自注意力和前馈层参数。
loss 降低表示训练目标拟合更好；是否推荐得更好，要看独立验证结果。

## 8. 如何推荐：编码历史后给候选打分

`predict()` 取最后一个位置的历史表示，然后与传入候选物品向量做点积。
按分数从高到低排序即可得到 Top-K。
`predict()` 不会自动决定候选集合，也不会自动屏蔽历史物品；这些由调用者处理。
分数是排序用的 logit，不能直接当成经过校准的点击概率。

SASRec 本身可以对全物品打分，也可以对一个候选子集打分。
大规模系统可以另接近似向量检索；此仓库的默认评估没有 ANN 环节。

## 9. 上游评估的具体口径

测试函数为每个用户构造 1 个真实目标 + 100 个随机物品，合计 101 个候选。
若用户超过 10,000，随机抽取 10,000 个用户评估。
返回 HR@10 和 NDCG@10：前者看真实物品是否进前 10，后者进一步考虑它排第几。

随机候选只排除训练历史，不保证互不重复，也没有全面排除当前目标或验证物品。
所以运行之间指标可能波动，候选集合也不够严格。
这些结果不能直接与 TIGER 对全目录生成推荐的指标放在同一张比较表。

此外 `main.py:129` 的保存条件同时检查验证指标和测试指标的改善。
正式基线需要只用验证集选择模型，最终再评一次测试集。
本次保留上游源码供阅读，这些修正属于下一步正式训练适配。

## 10. 从当前版本走向 TIGER

共享部分：原始交互、清洗、ID 映射、用户划分、物品目录、评测规则。
新增部分：用 `items.jsonl` 编码物品文本，训练 RQ-VAE，建立数字物品 ID 与语义 ID 的双向映射。

当前有 28 个物品缺少元数据，已在 `missing_metadata_asins.json` 中列出。
它们的文本字段留空，不伪造标题。TIGER 前需要补齐、设计缺失表示，或统一重建过滤后的实验数据；
不能只在 TIGER 中删除它们，却继续使用当前 SASRec 指标作直接对比。

```text
SASRec：历史数字 ID → 历史表示 → 给物品向量打分 → Top-K
TIGER： 历史语义 ID → 生成下一物品的语义 ID → 映射真实物品 → Top-K
```

物品内容相似只提供一部分信息，个性化仍需要用户历史。
TIGER 不一定超过 SASRec；逐步检查语义编码质量、合法解码、训练与评测一致性，再决定是否扩大模型。

下一步的实际顺序是：准备独立训练环境 → 小规模通路检查 → 修正全目录评测和验证集选模型 →
训练普通基线 → 接入 TIGER。
